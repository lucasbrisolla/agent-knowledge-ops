candidato 01 / transversal / implementado

Contrato de projeto de fonte entregue

● Implementado
arquivos

source_project/core.py · tools/validate-source-project.py · tools/create-source-project.py · tools/create-book-collection.py · schemas/source-project.schema.md

problema original

O schema descrevia uma única forma de projeto, mas cada fluxo conhecia uma variação própria. Estrutura, status e destino eram verificados em vários callers, com divergências entre livros, intake e YouTube.

implementação

source_project agora concentra diretórios, arquivos obrigatórios, tipos de fonte, estados, manifest, promotion matrix e validação. Os scripts continuam como adapters; perfis de livro e YouTube reutilizam o mesmo layout e deixam suas diferenças explícitas.

resultado

O comando validate-source-project.py dá feedback estruturado antes da escrita dos pipelines, e os testes cobrem projeto válido, campos inválidos, estrutura incompleta e avisos de diretórios vazios.

Deletion test: ao deletar o módulo, as regras de layout, status e separação entre raw/, library/ e promoção reaparecem em todos os callers. A complexidade não desaparece; ela se espalha.
Evidências pós-implementação: contrato em `source_project/core.py:1-169`; CLI em `tools/validate-source-project.py`; integração nos criadores e no intake; testes em `tests/test_validate_source_project.py` e `tests/test_create_book_collection.py`.

candidato 02 / pipeline existente / alinhado

Biblioteca de YouTube alinhada ao projeto de fonte

● Alinhado
arquivos

problema original

O script misturava descoberta, classificação, parsing, renderização e escrita. Também partia de Path.cwd() e produzia videos/ e index.md fora do contrato geral de library/.

implementação

A CLI agora aceita --project, valida o projeto e grava em library/videos, library/index.md e library/README.md. O modo legado por diretório corrente foi preservado para compatibilidade.

candidato 03 / mudança local / implementado

Intake de livros com commit transacional

● Implementado
arquivos

tools/extract-book-source.py · tests/test_extract_book_source.py · skills/book-source-intake/SKILL.md

problema original

O intake concentrava configuração, subprocesso, contrato JSON, cópia de arquivos, metadados e renderização. A principal exigência era impedir que uma falha deixasse apenas parte de raw/ ou library/.

implementação

O fluxo valida o projeto canônico, normaliza a saída em ExtractorOutput, prepara os artefatos em diretório temporário e usa commit com backup e rollback. Sucesso grava exatamente texto, metadados e índice; falha preserva o estado anterior.

resultado

A garantia “ou todos os artefatos, ou nenhum” agora está concentrada no fluxo de materialização, com testes para sucesso, falha do extrator, overwrite, rollback e projeto incompleto.

Limite consciente: a profundidade foi obtida dentro do adapter atual. Um módulo separado só se justifica quando surgirem mais extratores, políticas de overwrite ou perfis editoriais.
Evidências pós-implementação: `tools/extract-book-source.py:37-169` define o resultado normalizado; `:302-375` materializa com commit/rollback; a cobertura está em `tests/test_extract_book_source.py`.

candidato 04 / contrato consolidado / implementado

Contrato único do agent_creator

● Implementado
arquivos

agent_creator/core.py · tools/create-agent-product.py · tools/agent_product.py · agent_creator/schemas/agent-product.schema.md

problema original

O seam em ProductSpec existia, mas campos, enums, escolhas da CLI e defaults podiam divergir. O contrato documentado em Markdown não era suficiente para impedir interpretações paralelas.

implementação

agent_creator.core agora expõe estados, formas recomendadas, status, usuário padrão e normalização de target_user. As CLIs e os adapters reutilizam esses valores, enquanto o schema Markdown continua como documentação do contrato.

resultado

Uma alteração nos valores canônicos alcança o core, a CLI e os adapters pelo mesmo seam. O teste de contrato verifica os valores compartilhados e a normalização do usuário opcional.

Próximo limite: o parser de frontmatter e os templates ainda são detalhes locais. Eles só precisam de uma nova abstração se surgirem outros formatos de entrada ou perfis de produto.
Evidências pós-implementação: valores canônicos em `agent_creator/core.py:61-86`; normalização em `:165-179`; reexportação em `agent_creator/__init__.py` e `tools/agent_product.py`; CLI alinhada em `tools/create-agent-product.py`.

status pós-implementação

A recomendação principal foi implementada

O seam de projeto de fonte agora concentra a estrutura executável, os estados e a validação. Isso reduziu a divergência entre livros e YouTube, deu ao intake de livros um commit seguro e alinhou o contrato do agent_creator. A revisão agora muda de “qual oportunidade explorar?” para “onde aprofundar somente se a variação justificar”.

Próximos passos proporcionais
  1. manter validate-source-project.py como gate dos novos pipelines;
  2. aprofundar o builder de YouTube apenas se surgirem novas regras de categoria;
  3. extrair o intake de livros para módulo próprio apenas com novos extratores ou perfis;
  4. registrar um ADR quando uma dessas decisões deixar de ser local.
Método: histórico Git, documentos canônicos, backlog, código e testes locais. Atualizado após a implementação dos tickets e os commits f3e9e82 e 1b8fc28. O relatório registra o estado arquitetural; não substitui a especificação nem os tickets.
