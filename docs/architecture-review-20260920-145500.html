candidato 01 / transversal

Aprofundar o contrato de projeto de fonte

● Strong
arquivos

tools/create-source-project.py · tools/create-book-collection.py · tools/extract-book-source.py · tools/build-youtube-library.py · schemas/source-project.schema.md

problema

O schema define uma única forma de projeto, mas cada fluxo conhece uma variação própria. O criador genérico cria sete pastas; a coleção de livros cria apenas README.md e índice; o intake de livros valida só raw/ e library/; o YouTube opera com videos/ e index.md na pasta corrente. O caller precisa aprender invariantes de estrutura, status e destino em vários lugares.

solução

Concentrar a estrutura, os caminhos de artefatos, os estados e a validação em um módulo profundo de projeto de fonte. Os scripts permanecem como adapters; perfis de livro, YouTube e outras fontes passam pelo mesmo seam, com diferenças explícitas onde realmente existem.

benefícios

Mais locality: uma mudança no contrato é corrigida uma vez. Mais leverage: cada novo intake reutiliza criação e validação. Os testes atravessam o seam do projeto e verificam o contrato completo, em vez de repetir verificações parciais em cada script.

Deletion test: ao deletar o módulo, as regras de layout, status e separação entre raw/, library/ e promoção reaparecem em todos os callers. A complexidade não desaparece; ela se espalha.
Evidências: schema em `schemas/source-project.schema.md:5-39`; layout YouTube em `skills/youtube-channel-intake/SKILL.md:17-25`; validação parcial em `tools/extract-book-source.py:82-110`; backlog já aponta o validador de projeto como próximo melhor passo.

candidato 02 / pipeline existente

Aprofundar a biblioteca de YouTube no seam do projeto

● Strong
arquivos

tools/build-youtube-library.py:1-412 · skills/youtube-channel-intake/SKILL.md:17-52 · schemas/youtube-channel-library.schema.md

problema

Um único script mistura descoberta de arquivos, classificação, escolha de legenda, parsing de SRT, normalização, geração de notas, índice e README. Ele parte de Path.cwd() e escreve videos/, index.md e README.md, enquanto o contrato geral fala em library/. Não há testes dedicados do builder no inventário atual.

solução

Transformar a biblioteca de YouTube em um módulo profundo que recebe um projeto de fonte e esconde parsing, classificação, renderização e política de sobrescrita. O adapter de CLI apenas traduz argumentos e relata o resultado.

benefícios

Aumenta depth na interface do pipeline: callers não precisam conhecer detalhes de SRT, slugs ou tabelas Markdown. Gera locality para mudanças na taxonomia e melhora testes de casos como legenda ausente, título inválido e regras customizadas.

Evidências: orquestração em `tools/build-youtube-library.py:50-94`; escrita de nota em `:178-238`; parsing de SRT em `:241-263`; a própria skill ainda prescreve uma estrutura paralela à do projeto de fonte.

candidato 03 / mudança local recente

Dar profundidade transacional ao intake de livros

● Worth exploring
arquivos

tools/extract-book-source.py:29-317 · tests/test_extract_book_source.py:121-196 · docs/superpowers/specs/2026-08-06-book-intake-integration-design.md:35-80

problema

O novo script concentra configuração, resolução do extrator, validação do projeto, subprocesso, contrato JSON, cópia de arquivos, enriquecimento de metadados e renderização de Markdown. A proteção contra artefatos parciais é boa, mas os testes conhecem o comportamento principalmente por meio de um processo falso; o dicionário de metadados e a renderização continuam acoplados ao fluxo de filesystem.

solução

Concentrar o workflow de intake em um módulo profundo com tipos internos para resultado do extrator, metadados e artefatos finais. Manter o subprocesso e a CLI como adapters internos/externos, preservando o diretório temporário e o commit final somente após sucesso.

benefícios

Mais locality para a garantia “ou todos os artefatos, ou nenhum”; mais leverage para adicionar campos ao índice, validar metadados ou trocar a política de overwrite. Testes podem atravessar o seam do contrato sem depender de cada detalhe do processo externo.

Cuidado: esta é uma mudança recém-adicionada. O ganho só paga a abstração se o intake ganhar variações reais ou continuar recebendo mudanças; caso contrário, manter o script e apenas extrair testes de contrato pode ser suficiente.
Evidências: o módulo tem 317 linhas; o teste cobre sucesso, falha, overwrite e projeto incompleto, mas via CLI e extrator falso. A especificação já descreve explicitamente o contrato raw/ + library/.

candidato 04 / contrato já extraído

Tornar o contrato do agent_creator realmente único

● Speculative
arquivos

agent_creator/core.py:47-176 · tools/create-agent-product.py:19-74 · tools/agent_product.py:1-29 · agent_creator/ARCHITECTURE.md

problema

O módulo já tem um seam promissor em ProductSpec, mas o contrato é repetido: campos e enums vivem no core, escolhas e defaults vivem na CLI, e o schema vive em Markdown. Há pequenas assimetrias: o core aceita estados e formas que a CLI não expõe; target_user existe no objeto, mas não é obrigatório em REQUIRED_FIELDS; o parser de frontmatter é manual.

solução

Consolidar normalização, campos obrigatórios, enums e defaults em um único módulo de contrato. As duas CLIs, o validador e o arquivo de schema tornam-se adapters da mesma fonte de verdade; detalhes de parsing e templates ficam atrás do seam.

benefícios

Mais depth para callers: eles aprendem uma regra, não três. Mais leverage quando a especificação evoluir e mais locality para mensagens de erro e validação. O teste de contrato pode provar que CLI, Markdown e scaffold convergem para o mesmo resultado.

Por que é especulativo: a extração de `agent_creator` é recente e já reduziu bastante a duplicação. Só vale reabrir se surgir um segundo perfil de produto, novas transições de estado ou uma mudança frequente no schema.
Evidências: `core.py:61-76` define enums; `create-agent-product.py:34-54` define subconjuntos diferentes; `schemas/agent-product.schema.md` redireciona para o schema canônico, mas não é a fonte executável.

top recommendation

Começar pelo contrato de projeto de fonte

É o seam com maior leverage: toca o backlog explícito do validador de projeto, reduz a divergência entre livros e YouTube e oferece uma base para o intake de livros sem forçar uma abstração prematura dentro dele. A pergunta para a próxima etapa é se os perfis devem compartilhar uma estrutura única ou apenas um contrato comum com adaptações documentadas.

Sequência sugerida
  1. mapear invariantes já existentes;
  2. definir o que é comum e o que é perfil;
  3. testar o contrato com book e YouTube;
  4. só então decidir se o intake de livros também precisa de extração interna.
Método: histórico Git, documentos canônicos, backlog, código e testes locais. Mudanças locais foram preservadas. O relatório é uma exploração arquitetural; não altera o repositório.
